# Kong Mesh Global Control Plane Migration to Konnect

## 1. Purpose

This document is the review and execution plan for migrating the existing
self-managed Kong Mesh Global Control Plane to Kong Konnect Mesh Manager. It
defines the scope, migration strategy, prerequisites, execution steps,
checkpoints, risks, validation, and rollback criteria.

Current environment:

- One Kubernetes zone
- Two meshes
- Kong Mesh Zone Control Plane version 2.13.10
- Konnect region: `au`
- Target KDS address: `grpcs://au.mesh.sync.konghq.com:443`
- The Zone Control Plane remains in the existing Kubernetes cluster
- Konnect becomes the managed Global Control Plane

This plan assumes the following CA strategy:

> Do not migrate the old CA or signing keys. Let Konnect create a new built-in
> CA for each mesh, then restart the Zone CP, Zone Ingress/Egress, and all mesh
> workloads during a maintenance window to establish the new trust domain.

If the business cannot accept a maintenance window or a full workload restart,
use the alternative strategy of migrating the old CA and rotating it later. Do
not execute the default cutover procedure without approving one of these two
strategies.

---

## 2. Target Architecture

Before migration:

```text
Self-managed Global CP
          |
          | KDS
          v
Kubernetes Zone CP
          |
          +-- Mesh A workloads
          +-- Mesh B workloads
```

After migration:

```text
Konnect-managed Global CP (AU)
          |
          | KDS over gRPC/TLS 443
          v
Existing Kubernetes Zone CP
          |
          +-- Mesh A workloads
          +-- Mesh B workloads
```

After migration, Konnect is the source of truth for:

- Mesh definitions
- Mesh policies
- Mesh-scoped secrets
- `ExternalService` and `MeshExternalService` resources
- Global policies and mesh configuration

The Zone CP remains responsible for:

- Managing dataplane proxies in its zone
- Managing Zone Ingress and Zone Egress
- Reporting runtime state and insights to Konnect
- Receiving mesh configuration and policies from Konnect

## 3. Resource Migration Scope

### 3.1 Resources to migrate or recreate

| Resource | Action | Notes |
|---|---|---|
| `Mesh` | Create or update in Konnect | Both meshes must exist with approved names and configuration |
| Mesh policies | Export, review, and import | Includes traffic permissions, routes, timeouts, retries, and other policies |
| `ExternalService` / `MeshExternalService` | Import into the correct mesh | These are desired-state business resources |
| mTLS configuration | Recreate in Konnect | The default strategy uses new built-in CAs |
| `AccessRole` | Recreate as required | Retain only required fine-grained Mesh write access |
| `AccessRoleBinding` | Map and recreate | Subjects must map to Konnect user email addresses or teams/groups |
| Zone Connector system account | Create in Konnect | Grant only the `Connector` role on the target Mesh Control Plane |
| Policy Manager system account | Create in Konnect | Keep policy-management and Zone Connector identities separate |

### 3.2 Resources not migrated

These resources are runtime or status resources and are regenerated:

| Resource | Reason |
|---|---|
| `Zone` | Registered automatically when the Zone CP connects to KDS |
| `ZoneInsight` | Generated from Zone connectivity state |
| `MeshInsight` | Generated by Konnect from current mesh state |
| `ServiceInsight` | Generated from dataplane and service state |
| `Dataplane` / `DataplaneInsight` | Re-registered after Kubernetes workloads restart |
| Zone Ingress/Egress insights | Generated when those components reconnect |

### 3.3 Secrets excluded by the default strategy

The default strategy does not import:

- Old built-in CA certificate/private key pairs
- Old dataplane token signing keys
- Old zone token signing keys
- Old user token signing keys
- `admin-user-token`
- Kubernetes ServiceAccount tokens
- Helm release secrets
- Admission webhook TLS secrets

The Konnect Zone Connector uses a dedicated System Account Access Token with an
`spat_` prefix. Store it in Azure Key Vault and mount it read-only into the
Zone CP Pod through the Secrets Store CSI Driver. It must never be stored in
Terraform state, Git, workflow artifacts, or logs.

## 4. CA and Signing-Key Strategy

### 4.1 Default: create new CAs

Konnect establishes a new trust root for each mesh. Existing sidecars retain
certificates signed by the old CA and do not trust certificates issued by the
new CA.

Required actions:

- Restart the Zone CP
- Restart Zone Ingress
- Restart Zone Egress, if enabled
- Restart every sidecar-enabled workload in both meshes
- Reissue tokens for any Universal dataplanes
- Recreate standalone Pods and Jobs; ensure future CronJob Pods use the new configuration

Old and new certificates can coexist during the cutover, so this approach
requires a maintenance window. Restarting only the Zone CP is not sufficient.

### 4.2 Alternative: migrate the old CAs

Use this strategy if the maintenance window or full restart is unacceptable:

1. Export the old Global CP with `kumactl export --profile=federation-with-policies`.
2. Convert each old built-in CA into a provided CA that references the exported certificate and key.
3. Import the old signing keys, meshes, and policies into Konnect.
4. Connect the Zone and validate existing dataplanes.
5. Rotate to a new CA later using the supported CA rotation procedure.

The export contains private keys. It must use encrypted storage and controlled
transfer and must never enter Git, Terraform state, CI artifacts, or logs.

### Checkpoint CP-0: CA strategy approved

- [ ] The business owner accepts the maintenance window and full workload restart
- [ ] The security team approves replacing the old trust roots
- [ ] No Universal dataplane depends on an old dataplane token
- [ ] If any item fails, select the old-CA migration strategy and repeat the review

## 5. Prerequisites

### 5.1 Konnect

- [ ] The target Mesh Global Control Plane exists in the AU region
- [ ] The correct Mesh Control Plane ID is recorded
- [ ] The mapping of the two existing mesh names is approved
- [ ] A Connector system account exists with only the `Connector` role
- [ ] Its role is scoped to the correct Mesh Control Plane and `au` region
- [ ] The Connector SAT exists and has not been written to logs or Terraform state
- [ ] The Policy Manager identity and permissions are approved

### 5.2 Azure Key Vault and AKS

- [ ] The Connector SAT is stored in Azure Key Vault
- [ ] A `SecretProviderClass` exists in `kong-mesh-system`
- [ ] AKS Workload Identity or Managed Identity can read the secret
- [ ] The token file is present and non-empty in the Zone CP Pod without printing its value
- [ ] The token mount is read-only

### 5.3 Network

- [ ] The Zone CP Pod resolves `au.mesh.sync.konghq.com`
- [ ] Internal cluster DNS and public DNS both work
- [ ] The egress firewall/proxy permits `au.mesh.sync.konghq.com:443`
- [ ] NetworkPolicy permits UDP and TCP port 53 to cluster DNS
- [ ] NetworkPolicy permits outbound TCP port 443 from the Zone CP
- [ ] Corporate TLS inspection does not break KDS gRPC/TLS

### 5.4 Version and compatibility

- [ ] Kong Mesh 2.13.10 compatibility with required Konnect features is confirmed
- [ ] Helm values and the post-renderer have been tested outside production
- [ ] All CRDs and policy types have passed compatibility review
- [ ] The current Helm release, chart version, and complete values are recorded

### Checkpoint CP-1: ready to prepare the migration

Go criteria: all prerequisites pass, including DNS resolution and TCP 443
connectivity.

No-Go criteria:

- DNS returns `Name or service not known`
- The KDS endpoint is unreachable
- Connector role, CP ID, scope, or region is unconfirmed
- The token file is missing or empty
- The maintenance window is not approved

## 7. Configure Konnect

### 7.1 Create the two meshes

Review these fields for each mesh:

- `constraints.dataplaneProxy.requirements`
- `meshServices.mode`
- `mtls.backends`
- `mtls.enabledBackend`
- `networking`
- `routing`
- `skipCreatingInitialPolicies`

Default CA parameters:

```text
type: builtin
RSA bits: 2048
CA expiration: 10y
dataplane certificate rotation: 1d
```

Matching the old CA name, RSA size, and expiration does not preserve its
identity. Konnect generates a new certificate and private key.

### 7.2 Import desired-state resources

Recommended order:

1. Mesh definitions
2. `ExternalService` / `MeshExternalService`
3. Baseline security policies
4. Routing, retry, timeout, observability, and other policies
5. `AccessRole` and mapped `AccessRoleBinding` resources

If `skipCreatingInitialPolicies=true` and mTLS is enabled, create the required
`MeshTrafficPermission` before production workloads connect. Otherwise, traffic
may be denied by default.

### Checkpoint CP-3: Konnect configuration complete

- [ ] Both meshes exist in Konnect with the approved configuration
- [ ] Both meshes use the intended new built-in CAs
- [ ] Required traffic permissions exist
- [ ] External services are verified
- [ ] Policy counts and critical fields match the approved inventory
- [ ] RBAC has been tested with representative identities
- [ ] The production Zone KDS address has not yet changed

## 8. Zone CP Connection Configuration

The key Kong Mesh 2.13.10 settings are:

```text
KUMA_MODE=zone
KUMA_MULTIZONE_ZONE_NAME=<existing-zone-name>
KUMA_MULTIZONE_ZONE_GLOBAL_ADDRESS=grpcs://au.mesh.sync.konghq.com:443
KMESH_MULTIZONE_ZONE_KONNECT_CP_ID=<konnect-control-plane-id>
KMESH_MULTIZONE_ZONE_KDS_AUTH_CP_TOKEN_PATH=/mnt/secrets-store/cp-token
```

The correct global-address variable is:

```text
KUMA_MULTIZONE_ZONE_GLOBAL_ADDRESS
```

Keep the existing Zone name. Do not start a second Zone CP with the same name.

### Checkpoint CP-4: final cutover Go/No-Go

Go criteria:

- [ ] All Konnect configuration checkpoints pass
- [ ] Connector token mount test passes
- [ ] DNS and TCP 443 tests pass
- [ ] The maintenance window has started
- [ ] Application teams are available
- [ ] Rollback operator and decision owner are available
- [ ] The old Global CP remains healthy and reconnectable

No-Go: any critical owner is unavailable or any network, token, RBAC, or policy
validation has failed.

## 9. Cutover Runbook

### 9.1 Freeze changes

- Pause Mesh and policy changes on the old Global CP
- Pause affected application deployments
- Record the cutover start time
- Capture the final resource inventory and health baseline

### 9.2 Update the Zone CP

Update the Zone CP through Helm values and the post-renderer:

- Preserve the existing Zone name
- Set the AU KDS address
- Set the Konnect Mesh Control Plane ID
- Mount the Connector SAT from Key Vault
- Never put the token in values, command-line arguments, or logs

Wait for the rollout:

```bash
kubectl --context "$ZONE_CONTEXT" -n kong-mesh-system \
  rollout status deployment/kong-mesh-control-plane --timeout=5m
```

### 9.3 Validate KDS connectivity

```bash
kubectl --context "$ZONE_CONTEXT" -n kong-mesh-system \
  logs deployment/kong-mesh-control-plane -c control-plane --since=30m |
grep -Ei 'kds|konnect|connected|secret|certificate|unauth|permission|error'
```

Error guide:

| Error | Check first |
|---|---|
| `Unauthenticated` | Invalid, expired, or incorrectly mounted token |
| `PermissionDenied` | Connector role, CP ID, scope, and region |
| `no such host` | Pod DNS, CoreDNS, and upstream DNS |
| `deadline exceeded` | Firewall, proxy, and NetworkPolicy |
| `x509` | TLS inspection and proxy trust configuration |
| Secret conflict | Old Kuma secrets still present in the Zone |

### Checkpoint CP-5: Zone connected to Konnect

- [ ] Konnect displays the existing Zone name
- [ ] Zone status is `Online`
- [ ] Zone CP logs have no persistent KDS, authentication, or TLS error
- [ ] Both mesh configurations are synchronized to the Zone
- [ ] The team accepts the transitional state before all workloads restart

If this checkpoint fails, start rollback and do not restart application
workloads.

### 9.4 Resolve old CA secret conflicts

Under the default strategy, the Zone may still contain same-named secrets
previously synchronized from the old Global CP. Kong Mesh 2.10 and later does
not overwrite a conflicting secret already present in the Zone.

List and review each secret:

```bash
kubectl --context "$ZONE_CONTEXT" -n kong-mesh-system \
  get secrets --field-selector='type=system.kuma.io/secret' \
  -o custom-columns='NAME:.metadata.name,MESH:.metadata.labels.kuma\.io/mesh,TYPE:.type'
```

Delete only CA/signing secrets that are confirmed to belong to the old trust
domain and are preventing new CA synchronization. Never use a wildcard bulk
delete and never delete the Konnect Connector token. Record every resource and
obtain change-owner approval before deletion.

Restart the Zone CP after cleanup, then verify secret synchronization and logs.

### 9.5 Restart the dataplane in batches

Recommended order:

1. Zone Ingress and Zone Egress
2. A non-critical workload or canary
3. Validate canary mTLS and business calls
4. Remaining Mesh A workloads
5. Remaining Mesh B workloads
6. StatefulSets, DaemonSets, standalone Pods, Jobs, and CronJobs

Deployment example:

```bash
kubectl --context "$ZONE_CONTEXT" -n <namespace> rollout restart deployment
kubectl --context "$ZONE_CONTEXT" -n <namespace> \
  rollout status deployment/<name> --timeout=5m
```

Do not restart the entire cluster without an approved inventory. Complete the
health checks for each batch before continuing.

### Checkpoint CP-6: validate every workload batch

- [ ] New Pods contain the sidecar
- [ ] Pods are Ready and replica counts are correct
- [ ] Dataplanes appear Online in Konnect
- [ ] There are no certificate or unknown-authority errors
- [ ] There are no dataplane `Unauthenticated` errors
- [ ] Calls within the same mesh succeed
- [ ] Cross-mesh calls match the intended policies
- [ ] External-service calls succeed
- [ ] Error rate, latency, throughput, and resource usage are normal

Stop subsequent batches after any failure. Fix the issue or initiate rollback
according to the agreed thresholds.

## 11. Rollback Plan

### 11.1 Rollback triggers

Evaluate immediate rollback if any of these conditions occurs:

- The Zone cannot connect to Konnect within the agreed time
- DNS, firewall, or proxy issues cannot be resolved within the window
- A significant number of dataplanes cannot re-register
- mTLS fails broadly
- A critical policy is missing or behaves differently
- A critical business smoke test fails
- Error rate or latency exceeds the agreed threshold

Complete these thresholds before the change:

```text
Maximum Zone connection time:        __________
Maximum recovery time per batch:     __________
Maximum acceptable error rate:       __________
Maximum acceptable P95/P99 latency:  __________
Final rollback decision time:        __________
```

### 11.2 Rollback actions

1. Stop all remaining workload restarts.
2. Restore the old Global CP KDS address and authentication configuration in the Zone CP Helm values.
3. Roll back or upgrade the Zone CP Helm release.
4. Confirm that the Zone reconnects to the old Global CP.
5. Restart every workload already moved to the new CA so it receives the old trust chain again.
6. Validate dataplanes, policies, and business calls in the old environment.
7. Preserve logs and a cutover timeline for investigation.

Because the default strategy changes the CA, rollback also requires another
restart for workloads that already received the new CA. Do not delete the old
Global CP or its CA secrets during the observation period.

### Checkpoint CP-R: rollback complete

- [ ] The Zone is connected to the old Global CP
- [ ] Every migrated workload is back on the old trust chain
- [ ] Critical business checks pass
- [ ] The change freeze has been lifted or extended as appropriate
- [ ] Failure causes and follow-up actions are recorded

## 12. Observation Period and Decommissioning

Keep an approved observation period, for example three to seven days. During
this period:

- Keep the old Global CP recoverable but freeze its configuration
- Monitor Zone KDS connectivity
- Monitor dataplane online percentage
- Confirm certificate rotation works
- Monitor policies, external services, and business metrics
- Test the Connector token rotation process

### Checkpoint CP-8: approval to decommission the old Global CP

- [ ] The observation period is complete with no unresolved issue
- [ ] Konnect configuration is managed through IaC and version control
- [ ] The rollback window is formally closed
- [ ] Security, platform, and application owners approve decommissioning
- [ ] Destruction of old secrets has an approved procedure
- [ ] Operations documentation, on-call runbooks, and alerts are updated
